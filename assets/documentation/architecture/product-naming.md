# OX-DX Product, Tool & Interface Naming

Future names must clarify responsibility.

They must not create semantic overlap.

## Product qualification rules

A future OX-DX product must have:

1. clear responsibility;
2. clear boundary;
3. a specific audience;
4. no semantic overlap with an existing owner;
5. no duplicate ownership;
6. no unnecessary rename of stable technical components;
7. no religious appropriation;
8. no marketing hype in technical names.

A product should remain understandable even when the OX-DX prefix is removed.

## Public extension pattern

Default:

**OX-DX + clear noun**

Potential patterns:
- OX-DX Web
- OX-DX Docs
- OX-DX CLI
- OX-DX SDK
- OX-DX Explorer
- OX-DX Console

These are naming patterns. They are not automatically approved products or existing repositories.

## Engine

Canonical engine name:

**Universal Ontology Engine**

Use for the Rust implementation.

Do not randomly alternate with:
- OX engine;
- DX engine;
- Universal engine;
- OX-DX engine.

## Specification

Public umbrella label:

**OX-DX Specification**

Normative technical object:

**Universal Ontology**

Normative filenames remain technically named.

The brand can point to the specification. It does not rename the specification.

## Tools

Tools should generally use concise functional names.

Good:
- inspect
- discover
- validate
- parse
- query — only when implemented

Avoid cute one-off names for ordinary utilities.

Public namespace may become `ox-dx`; underlying capability names should remain technical.

## Interfaces

An interface is a user-facing interaction surface such as:
- web;
- API;
- visualization;
- console;
- explorer.

Each interface must answer:

> What does this expose that another existing interface does not already own?

If the answer is unclear, do not create another interface brand.

## Documentation

Public property:

**OX-DX Docs**

Current technical documentation remains where it is while coupled to the engine.

Move to a dedicated documentation product/repository only for a real lifecycle, audience, deployment, or governance reason.

## Community

Public community umbrella:

**OX-DX Community**

Potential channels:
- GitHub Discussions;
- future chat/forum;
- contributor portal.

Do not invent a separate community brand.

## Quranic naming boundary

Quranic inspiration may shape reflection around order, measure, signs, knowledge, relation, observation, and meaning.

It must not be converted into:
- sacred tool names;
- invented Arabic product names;
- divine validation claims;
- commercial spiritual authority.

Technical product naming remains precise and neutral.

## Gen-Z / grunge boundary

Short and memorable is good.

Confusing foundational infrastructure is not.

Use Gen-Z clarity and grunge attitude in:
- voice;
- launch/editorial presentation;
- campaigns;
- visual identity.

Do not use meme naming for:
- ontology;
- schemas;
- graph;
- engine;
- core libraries;
- identity contracts.

## Product creation gate

Before naming a new product:

1. write its one-sentence responsibility;
2. name its owner;
3. name what it explicitly does **not** own;
4. identify whether it needs an independent lifecycle;
5. verify there is no existing product/tool/interface with the same responsibility;
6. only then choose a name.

**Architecture first. Name second.**
