# OX-DX Brand Governance — v1.0

Brand Bible v1.0 is the first stable canonical OX-DX brand system.

It is not “final forever.”

## Status vocabulary

### CANONICAL
Source of truth for a defined brand concern.

### APPROVED
Valid derivative, application, or supporting material consistent with canonical sources.

### EXPERIMENTAL
Review-only work that must not silently become default/public identity.

### DEPRECATED
Retained for migration/history but not recommended for new work.

## Who can change the brand

Canonical changes require explicit approval from:
- the project owner; or
- a designated brand maintainer acting under an explicit project decision.

Automation may regenerate derived assets/status data but may not redefine canonical brand rules.

## Changes requiring explicit approval

Explicit approval is required for:
- OX-DX name;
- descriptor;
- technical engine name;
- master logo geometry;
- master icon/wordmark;
- core palette;
- canonical taglines;
- brand promise;
- voice formula;
- Quranic positioning boundary;
- naming hierarchy;
- visual grammar fundamentals;
- Brand Bible major/minor version;
- promotion of EXPERIMENTAL assets to CANONICAL.

## What may evolve without a brand-version change

Within existing rules, maintainers may:
- create new compliant application layouts;
- add documentation examples;
- export new raster sizes/formats;
- improve accessibility;
- clarify wording without changing meaning;
- create derived diagrams/social/release assets from canonical primitives;
- add implementation guidance that does not alter the brand contract.

## Experimental assets

Experimental work must:
1. be marked **EXPERIMENTAL**;
2. live outside master identity paths;
3. not replace default assets;
4. state the question being tested;
5. identify the canonical source it is exploring;
6. be reviewed before promotion.

## Promotion

Promotion to APPROVED or CANONICAL requires:
- documented purpose;
- consistency audit;
- accessibility check;
- duplication check;
- semantic-boundary check;
- explicit approval where required;
- asset index/status update.

## Deprecation

Deprecation must:
- preserve the old asset/reference when migration history matters;
- mark status **DEPRECATED**;
- identify the replacement;
- avoid breaking links without reason;
- never delete technical history solely for cosmetic consistency.

## Change control

Every canonical brand change must answer:

### WHY?
What evidence/problem requires a change?

### WHAT CHANGES?
Which canonical rule, asset, term, or surface changes?

### WHAT REMAINS?
What identity/compatibility must remain stable?

### WHAT BREAKS?
Which consumers/assets/docs become incompatible?

### WHAT NEEDS MIGRATION?
What paths, files, references, templates, or guidance must move?

A change without defensible answers should not proceed.

## Brand versioning

### v1.0
First canonical stable OX-DX brand system.

### v1.x
Backward-compatible evolution:
- clarification;
- additive approved applications;
- accessibility improvement;
- additional examples;
- minor token/application refinement that preserves identity.

### v2.0
Potentially breaking brand change:
- master identity geometry;
- core naming hierarchy;
- primary brand promise/descriptor;
- major visual grammar replacement;
- major canonical palette/voice architecture change.

Do not bump major version for ordinary campaign work.

## Authority hierarchy

For brand questions:
1. `OX-DX-BRAND-BIBLE-v1.0.md`;
2. Brand Bible specialist files;
3. canonical specialist documents explicitly referenced by the Bible;
4. approved application guidance;
5. derived assets;
6. experimental work.

For technical semantics, normative specifications/standards/implementation still outrank brand prose.

## One-system rule

No new brand subsystem is created unless the current system cannot express a real requirement.

**CONVERGENCE, NOT ACCUMULATION.**
