# OX-DX Communication Checklist

Before publishing README copy, documentation, issue text, PR descriptions, release notes, CLI copy, social posts, papers, or future UI language, ask:

- [ ] Is it true at the stated scope?
- [ ] Is the claim supported by repository evidence or clearly marked as philosophy/proposal?
- [ ] Is it clear?
- [ ] Does it use canonical OX-DX terminology?
- [ ] Does it preserve the distinction between evidence and truth?
- [ ] Does it preserve provenance instead of confusing provenance with identity?
- [ ] Does it distinguish containment, projection, observation, and representation?
- [ ] Does it distinguish current implementation from roadmap?
- [ ] Does it use the exact maturity vocabulary where status matters?
- [ ] Does it sound like OX-DX: calm, deep, direct, sharp, precise?
- [ ] Does it avoid corporate/startup hype?
- [ ] Does it preserve the philosophical/engineering boundary?
- [ ] Does Quranic inspiration remain philosophical rather than technical authority?
- [ ] Does Gen-Z clarity improve speed without becoming childish?
- [ ] Does grunge attitude challenge bad assumptions rather than people?
- [ ] Can the reader reach a normative source, implementation, test, or release record for important technical claims?
- [ ] Are version numbers correctly distinguished between ontology contract and engine release?
- [ ] Are volatile status/version claims generated or freshly verified?
- [ ] Have unsupported superlatives been removed?
- [ ] If evidence is missing, does the text say so?

## Final four

**Say what was observed.**

**Say what was inferred.**

**Say what was implemented.**

**Say what remains unknown.**
