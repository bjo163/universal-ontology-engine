# OX-DX Product UI Do / Don't

## DO

### Use evidence before interpretation
Let users reach the material that supports a classification or relation.

### Use graph relationships
Keep containment, projection, observation, representation, and other relations distinct.

### Use negative space intentionally
A void may communicate unknown, scope, boundary, pause, or unresolved detail.

### Use asymmetry with purpose
Let context and focus occupy unequal visual weight when the task demands it.

### Use subtle grunge
Keep geometry clean. Let deterministic surface friction appear only where it supports the brand.

### Use technical labels
Use exact TYPE, KIND, relation, source, status, or operation terms when they matter.

### Use clear provenance
Keep source/path/revision/span reachable without turning them into identity.

### Use conventional controls when convention is clearer
OX-DX originality comes from system logic, not forcing every checkbox/search/close icon into a custom shape.

## DON'T

### Turn everything into cards
An OX-DX information surface is not a rounded card with a border.

### Use generic neon UI
Dark background + cyan glow is not enough to be OX-DX.

### Use fake code as decoration
Technical text must be real or clearly illustrative.

### Use random node graphs
Only visualize relationships the data actually defines.

### Use color to imply unsupported meaning
Color reinforces a label/geometry; it never invents status.

### Hide evidence behind interpretation
Summary and projection must remain traceable to source evidence.

### Use animation without purpose
Motion reveals relation, witness, state, or resolution.

### Use Quranic text as interface decoration
Philosophical inspiration does not become religious UI ornament.

### Use AI as visual identity
Future AI assistance remains subordinate to evidence and inspection.

### Force 49 levels into a visible tree
The ontology is a resolution spine over a graph, not a mandatory folder hierarchy.
